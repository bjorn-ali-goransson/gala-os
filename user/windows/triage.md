## About these results

- run-all.ps1's `fault` field cannot work as written: it reads the Application log's Application Error event (1000), and the runner sets SEM_NOGPFAULTERRORBOX (so crash.exe opens no dialog), which the children inherit and which stops a faulting process reporting to Windows Error Reporting. The log holds no such event from either sweep while holding four older ones, so every entry, crashes included, reads "no Application Error event found". user/windows/fault.py gets the same three facts by debugging the program instead.
- Results are not stable between runs on the same machine. Comparing the two sweeps here: com_test 0x6c -> 0x6e, kernel32_system_test 0x58 -> 0x34, security_test 0x21 -> 0x4, pipe_test 0x137 -> 0x14b, process_test 0x47 -> 0x4a, persist_test 0 -> 0x38, tds_test's line went from "first start of the instance". Some of that is tests that keep state across runs (persist_test, tds_test), and some is ordering or timing. A single report does not pin a divergence down.
- Only the first failing check of a program is ever known, so fixing one may reveal the next; a count here is of programs, not of divergences.
- No test source or binary was changed, as the brief requires. The binaries are cross-compiled on Linux and CI checks user/bin against the sources, and there is no Rust toolchain on this machine.
- Some of what a run reports is leftover state rather than a difference: kernel32_file_test fails its first check only because %TEMP%\gala_k32 is still there from the run before. A program that leaves what it made behind reports a different check the second time, so a report is only clean on a clean machine.
- Which methods count a check is worked out per test rather than assumed, and has to be: the tests use eq and ok mostly, but also st, ok0, fails and wrappers of their own, the counter is a named field in session_test and a Cell in others, and some methods carry generic parameters. ### comctl32_test (0x00000038)

- check 56, source line 319
- asserts: `CHECK(SendMessageW(tt, TTM_ADDTOOLW, 0, (LPARAM)&ti));`
- windows: FlatSB_GetScrollProp(WSB_PROP_WINSTYLE) returns the window's WS_*SCROLL bits plus one low bit per scroll bar: 0x2 for vertical, 0x4 for horizontal. For a WS_VSCROLL-only window, which is what the test creates, it returns 0x00200002 rather than WS_VSCROLL's 0x00200000.
- evidence: probed here against comctl32 5.82.26100.8328, loaded by full path. WS_VSCROLL only -> 0x00200002; WS_HSCROLL only -> 0x00100004; both -> 0x00300006; neither -> 0. The other properties the test sets read back exactly: VSTYLE 0, CXVSCROLL 21, VBKGCOLOR 0x00030201.
- note: A real divergence, and a one-bit one: the test asserts v == WS_VSCROLL and should mask or expect the extra bit. Also worth knowing for anyone probing this: in a process that activates comctl32 version 6, every FlatSB_GetScrollProp returns FALSE and leaves the output untouched, so the whole family has to be probed against version 5, which is what a test without a manifest gets.

### kernel32_thread_test (0x00000051)

- check 81, source line 458
- asserts: `c.eq(GetLastError().into(), 24)?;`
- windows: SetPriorityClass does not validate the value as a whole: it takes the recognised class bits out of it and the lowest class wins, IDLE first. A value carrying at least one recognised bit succeeds; a nonzero value carrying none is refused like 0, with FALSE and ERROR_INVALID_PARAMETER (87). REALTIME (0x100) returns TRUE but leaves the class at HIGH (0x80) without SeIncreaseBasePriorityPrivilege. The precedence among the recognised bits is a strict order, and it is the inverse of scheduling priority: the lowest class always wins. Over all fifteen pairs, IDLE beats all five others, BELOW_NORMAL four, NORMAL three, ABOVE_NORMAL two, HIGH one, and REALTIME none.
- evidence: probed here, resetting to NORMAL between calls. Recognised alone: 0x20->0x20, 0x40->0x40, 0x80->0x80, 0x4000->0x4000, 0x8000->0x8000, 0x100->1 err=0 but class 0x80. IDLE wins over the rest: 0x60, 0xc0, 0x140, 0x4040 all -> 0x40. 0x12345 (has 0x40 and 0x100) -> 0x40, and 0x12305, the same value with 0x40 cleared, -> 0x80 through its 0x100. No recognised bit: 0x1, 0x2, 0x8, 0x10, 0x200, 0x1000, 0x10000 all -> 0 err=87. Round 2, every pair probed: 0x4020 and 0x4080 -> BELOW_NORMAL, 0x8020 -> NORMAL, 0x8080 -> ABOVE_NORMAL, 0xa0 and 0x120 -> NORMAL, 0x180 -> HIGH, 0x4100 -> BELOW_NORMAL, 0x8100 -> ABOVE_NORMAL, 0xc000 -> BELOW_NORMAL, and every pair containing IDLE -> IDLE.
- note: A real divergence, and the rule is not the one it first looks like: it is not that the IDLE bit means IDLE, but that unrecognised bits are ignored while any recognised one decides, with IDLE taking precedence. Round 2, from ROADMAP WD Next item 1. So the Linux side's "gala takes the lowest class for now" is already right, and the test can assert it. Answers the open probe for two class bits with neither being IDLE's. Round 3: the tests now print their own failing line, so the mapping is exact and no longer counted.
