## About these results

- run-all.ps1's `fault` field cannot work as written: it reads the Application log's Application Error event (1000), and the runner sets SEM_NOGPFAULTERRORBOX (so crash.exe opens no dialog), which the children inherit and which stops a faulting process reporting to Windows Error Reporting. The log holds no such event from either sweep while holding four older ones, so every entry, crashes included, reads "no Application Error event found". user/windows/fault.py gets the same three facts by debugging the program instead.
- Results are not stable between runs on the same machine. Comparing the two sweeps here: com_test 0x6c -> 0x6e, kernel32_system_test 0x58 -> 0x34, security_test 0x21 -> 0x4, pipe_test 0x137 -> 0x14b, process_test 0x47 -> 0x4a, persist_test 0 -> 0x38, tds_test's line went from "first start of the instance". Some of that is tests that keep state across runs (persist_test, tds_test), and some is ordering or timing. A single report does not pin a divergence down.
- Only the first failing check of a program is ever known, so fixing one may reveal the next; a count here is of programs, not of divergences.
- No test source or binary was changed, as the brief requires. The binaries are cross-compiled on Linux and CI checks user/bin against the sources, and there is no Rust toolchain on this machine.
- Some of what a run reports is leftover state rather than a difference: kernel32_file_test fails its first check only because %TEMP%\gala_k32 is still there from the run before. A program that leaves what it made behind reports a different check the second time, so a report is only clean on a clean machine.
- Which methods count a check is worked out per test rather than assumed, and has to be: the tests use eq and ok mostly, but also st, ok0, fails and wrappers of their own, the counter is a named field in session_test and a Cell in others, and some methods carry generic parameters. Twelve mappings were wrong before that was handled, registry_test's among them, where the check moved from the ProductName line to the CurrentBuild line and the reported value then made sense.
- Round 2 (ROADMAP WD Next item 1): three of the open questions are answered in the entries above, under kernel32_thread_test (SetPriorityClass with mixed values), kernel32_sys_test (WriteConsoleA) and wait_test (NtCreateTimer's unknown type). The user-callback faults and oleaut32_test's and clusapi_test's last call are not: both need the program's own instrumentation, since the fault address is inside ntdll or a system DLL and attributing it to a call would need symbols for our own binaries, which this machine does not have. A fresh run-all.ps1 run is also still to come: the WD fixes are in the sources but user/bin has not been re-exported, so a sweep here would still run the old binaries and report the old checks.
- The brief's step 1 was deliberately not done: no galatest account was created and nothing ran elevated. access_test, logon_test and profile_test (ERROR_LOGON_FAILURE), restricted_test (not an administrator) and schannel_test (skipped) are therefore unresolved by choice, not by evidence.
- Round 2 sweep, against the binaries exported in 746404e7 (26200.9711): 76 programs exit 0, up from 71, and the entry count fell from 176 to 100 non-zero. All three access violations in our own binaries are gone (dwrite_test and wow64_seh_test now pass; kernel32_sync_test reaches a check instead of faulting), browser_api_test loads, and manifest_test, peb_test and wait_test pass. Seven moved to a later check as expected: kernel32_file_test 1 -> 40, kernel32_sys_test 4 -> 54, kernel32_thread_test 18 -> 36, kuser_test 9 -> 18, registry_test 8 -> 39, sspi_test 21 -> 48, wow64_test 11 -> 71. Nothing regressed. kernel32_file_test moving back to the check it failed on the very first clean run confirms its leftover-state fix. persist_test moved without being re-exported (0x38 -> 0x0e), which is its own state across runs, not a code change.
- run-all.ps1 keeps only the first line a program prints that starts with its name, so a program that prints anything informational before failing loses its failure message (quota_test is the case here). Keeping the last such line, or the one carrying "check", would make those diagnosable.
- Round 2, second batch (from user/windows/notes-from-linux.md): SetPriorityClass's precedence is answered above and confirms gala's current choice. The other open probe, REALTIME by a process whose token holds SeIncreaseBasePriority disabled, needs an elevated prompt and was not done: elevation was declined for this machine, so it stays open by choice rather than by evidence. run-all.ps1 now keeps the last line a program prints that starts with its name, as asked.

The tests are being changed to print their own failing line, which removes the guesswork; until then prefer the report line's own "(line L)" where a test gives one.

### comctl32_test (0x0000000d)

- check 13, source line 581
- asserts: `CHECK(FlatSB_GetScrollProp(w, WSB_PROP_WINSTYLE, &v) && v == WS_VSCROLL);`
- windows: FlatSB_GetScrollProp(WSB_PROP_WINSTYLE) returns the window's WS_*SCROLL bits plus one low bit per scroll bar: 0x2 for vertical, 0x4 for horizontal. For a WS_VSCROLL-only window, which is what the test creates, it returns 0x00200002 rather than WS_VSCROLL's 0x00200000.
- evidence: probed here against comctl32 5.82.26100.8328, loaded by full path. WS_VSCROLL only -> 0x00200002; WS_HSCROLL only -> 0x00100004; both -> 0x00300006; neither -> 0. The other properties the test sets read back exactly: VSTYLE 0, CXVSCROLL 21, VBKGCOLOR 0x00030201.
- note: A real divergence, and a one-bit one: the test asserts v == WS_VSCROLL and should mask or expect the extra bit. Also worth knowing for anyone probing this: in a process that activates comctl32 version 6, every FlatSB_GetScrollProp returns FALSE and leaves the output untouched, so the whole family has to be probed against version 5, which is what a test without a manifest gets.

### kernel32_thread_test (0x00000032)

- check 50, source line 348
- asserts: `c.eq(SetThreadDescription(t, name.as_ptr()) as u64, 0)?;`
- windows: SetPriorityClass does not validate the value as a whole: it takes the recognised class bits out of it and the lowest class wins, IDLE first. A value carrying at least one recognised bit succeeds; a nonzero value carrying none is refused like 0, with FALSE and ERROR_INVALID_PARAMETER (87). REALTIME (0x100) returns TRUE but leaves the class at HIGH (0x80) without SeIncreaseBasePriorityPrivilege. The precedence among the recognised bits is a strict order, and it is the inverse of scheduling priority: the lowest class always wins. Over all fifteen pairs, IDLE beats all five others, BELOW_NORMAL four, NORMAL three, ABOVE_NORMAL two, HIGH one, and REALTIME none.
- evidence: probed here, resetting to NORMAL between calls. Recognised alone: 0x20->0x20, 0x40->0x40, 0x80->0x80, 0x4000->0x4000, 0x8000->0x8000, 0x100->1 err=0 but class 0x80. IDLE wins over the rest: 0x60, 0xc0, 0x140, 0x4040 all -> 0x40. 0x12345 (has 0x40 and 0x100) -> 0x40, and 0x12305, the same value with 0x40 cleared, -> 0x80 through its 0x100. No recognised bit: 0x1, 0x2, 0x8, 0x10, 0x200, 0x1000, 0x10000 all -> 0 err=87. Round 2, every pair probed: 0x4020 and 0x4080 -> BELOW_NORMAL, 0x8020 -> NORMAL, 0x8080 -> ABOVE_NORMAL, 0xa0 and 0x120 -> NORMAL, 0x180 -> HIGH, 0x4100 -> BELOW_NORMAL, 0x8100 -> ABOVE_NORMAL, 0xc000 -> BELOW_NORMAL, and every pair containing IDLE -> IDLE.
- note: A real divergence, and the rule is not the one it first looks like: it is not that the IDLE bit means IDLE, but that unrecognised bits are ignored while any recognised one decides, with IDLE taking precedence. So an unknown value is refused when it carries no class bit at all, which means gala cannot simply accept every nonzero value either. The REALTIME downgrade is a second, separate thing to match. Round 2, from ROADMAP WD Next item 1. So the Linux side's "gala takes the lowest class for now" is already right, and the test can assert it. Answers the open probe for two class bits with neither being IDLE's. Round 3: the tests now print their own failing line, so the mapping is exact and no longer counted.
